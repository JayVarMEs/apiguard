# S0 demo

```bash
cd C:\cyberProject
python demo\run_s0_demo.py
```

Input: `specs/vampi_openapi3.yaml` — the real VAmPI OpenAPI 3 spec
(github.com/erev0s/VAmPI), which is APIGUARD's L3 ground-truth API in experiment E4.
`specs/vampi_swagger2.yaml` is a three-endpoint slice of the same API written as
Swagger 2.0, used only to show that both versions flatten to one internal form.

The run prints six sections:

1. **Input** — detected version, content hash (what T1 de-duplicates on), `|E(S)| = 14`.
2. **E(S)** — one row per (path, method): auth source, parameter / body / response counts.
3. **Signal a rule scanner does not see** — the endpoints with no security requirement
   that still return `password`, `admin`, `email`, `auth_token`. `GET /users/v1/_debug`
   is the headline: unauthenticated, and it returns every user's password. This is
   feature group C, and it is why S2 scores every endpoint rather than only flagged ones.
4. **One full record** — exactly what S2a will receive for one endpoint.
5. **Version independence** — the same endpoint from the OAS3 and the Swagger 2 file
   produces the same `operation_id`, `security_source`, `servers` and expanded response
   properties; the Swagger 2 `body` parameter has become a request body, and the
   path-level parameter has been merged into the operation.
6. **Corpus mode** — a deliberately broken spec is written to `parse_errors.jsonl`
   with its reason and counted in the parse-failure rate, never silently dropped.

Outputs land in `out/`:

| file | contents |
|---|---|
| `vampi_endpoints.jsonl` | 17 endpoint records, one JSON object per line (S2a input) |
| `parse_errors.jsonl` | the failure record for the broken spec |
| `demo_output.txt` | the console transcript, for pasting into the report |
| `broken_spec.yaml` | generated by the demo; the deliberate parse failure |

## Where the API spec files come from

| Source | What it is | How to get it |
|---|---|---|
| **APIs.guru** | 2,529 real APIs, CC0. APIGUARD's primary T1 corpus. | `python tools/fetch_apis_guru.py --limit 20 --out corpus/apis_guru` (index: `https://api.apis.guru/v2/list.json`) |
| **APIstic** | 1,275,568 specs mined from GitHub — the scale-up corpus (MSR 2024). | dataset link in the APIstic paper / its Zenodo release |
| **VAmPI** | Deliberately vulnerable API + its OAS3 spec. L3 ground truth. | `github.com/erev0s/VAmPI` -> `openapi_specs/openapi3.yml` (already in `demo/specs/`) |
| **OWASP crAPI** | Second vulnerable ground-truth API. | `github.com/OWASP/crAPI` -> `openapi-spec/` |
| **SwaggerHub / Postman / RapidAPI** | Public catalogues of individual specs. | download one spec at a time from the site |
| **GitHub code search** | Any repo shipping a spec. | search `filename:openapi.yaml` or `filename:swagger.json` |
| **Petstore** | The canonical toy spec, useful for a first smoke test. | `https://petstore3.swagger.io/api/v3/openapi.json` |

`demo/specs/apis_guru_sample/` holds a 12-API sample already downloaded from APIs.guru
(seed 42, snapshot 2026-09-08). Files are grouped one folder per provider, which is exactly
the grouping experiment E1's provider-grouped splits need, and `manifest.jsonl` records the
source URL and snapshot date of every file for the deliverable.

Run S0 over that sample:

```bash
set PYTHONPATH=src
python -m apiguard.core.normalizer demo\specs\apis_guru_sample ^
    -o demo\out\apis_guru_endpoints.jsonl -e demo\out\apis_guru_errors.jsonl --stats
```

Result on the sample: **12 specs parsed, 0 failed, 222 endpoints** — 139 from OpenAPI 3
files and 83 from Swagger 2.0 files, all in one internal form; security is `inherited` for
126 endpoints, `own` for 80 and absent for 16; the largest single endpoint expands to 496
response properties (which is why `MAX_PROPERTIES` exists).
